# Dunwell: chase unpaid invoices on a schedule, politely, then firmly

Slug: `dunwell`. For freelancers: given their invoices and today's date, decide which
reminder each invoice gets today, draft the email, and attach a payment link.

## 1. Input

`fixtures/invoices.json`: an array of
`{ id, client, amount_cents, due: "YYYY-MM-DD", paid_cents, last_reminder: { stage, date } | null, hold: boolean }`.

## 2. Decision rules (exact, graded)

For `today`, with `days_overdue = today − due` in calendar days and
`remaining = amount_cents − paid_cents`:

1. `remaining × 100 ≤ amount_cents` (1% or less unpaid, integer math) → `none`.
2. `hold` is true → `hold`.
3. `today` is a Saturday or Sunday → `none` (reminders go out on weekdays).
4. Stage by `days_overdue`: −3…−1 → `heads_up`; 0 → `none`; 1…6 → `friendly`;
   7…20 → `firm`; 21…44 → `final`; ≥ 45 → `escalate`; < −3 → `none`.
5. `heads_up` is only sent if there has never been a reminder (`last_reminder` is null);
   otherwise `none`.
6. No going back: stages are ordered `heads_up < friendly < firm < final < escalate`. If
   the computed stage is lower than `last_reminder.stage`, the action is `none`.
7. No repeats within 7 days: if the computed stage equals `last_reminder.stage` and
   `today − last_reminder.date < 7`, the action is `none`. On day 7 or later it repeats.

Rules apply in that order; the first one that decides wins.

## 3. Product

- Dashboard of invoices with today's action and why (which rule decided). A date picker to
  simulate any `today`.
- An email draft per action, tone escalating with the stage, generated by an LLM through
  `ai-kit/` in live mode; in demo mode, from committed templates (clearly labelled as
  templates, never presented as model output).
- A payment link per invoice: real payment-provider test-mode link only when its key is
  set; in demo mode a local mock checkout page that marks the invoice paid in the session.
- Sending email only when the mail key is set; in demo mode an on-screen outbox.

## 4. CLI scripts

| Script | Must do |
|---|---|
| `decide <invoices.json> --today YYYY-MM-DD` | Prints `{ "today", "decisions": [{ "id", "action", "rule": 1..7 or "stage" }] }` in input order. |
| `eval` | For each case in `fixtures/cases.json` (`{ today, invoices, expected: { [id]: action } }`) prints `{ "cases", "decisions", "accuracy", "score" }`, `score` = accuracy × 100. |

## 5. Graded number

**Decision accuracy** (actions only) over all invoices in hidden cases.

## Constants (identical in every tanda 1 brief)

### Stack (fixed)
- Bun as package manager and runtime. Next.js App Router. TypeScript strict, no `any`, no
  `@ts-ignore`. Tests with `bun test`. Linter of your choice.
- Money is integer cents, never floats.
- Required scripts: `dev`, `build`, `test`, `typecheck` (`tsc --noEmit`), `lint`, plus the
  project-specific CLI scripts in its brief. CLI scripts print JSON on stdout and nothing else.

### Demo mode (portfolio rule)
- The app must work fully with **no environment variables**: every external service (LLM,
  email, payments, analytics) has a demo path that uses committed fixtures.
- Optional live mode only when its env var is set. Never required for the page, the tests
  or the CLI scripts.
- If this project uses an LLM, `ai-kit/` (already in the repo, treat it as vendored) is
  the client: its `chat()` router (`ai-kit/router.ts`) falls back across free providers and
  is live when any of `GEMINI_API_KEY`, `GROQ_API_KEY` or `OPENROUTER_API_KEY` is set;
  `demo-mode.ts` has the demo helpers. Read the code, not only its README.

  unknown locale returns 404. `/{lang}` redirects to `/{lang}/app`.
- `/{lang}/app` is the product page. At its top-left, a link
  `https://portafolio-mdea.vercel.app/{lang}/projects` reading `← All projects` /
  `← Todos los proyectos`. A language switch EN/ES.

  "Compare" (real numbers computed by the product, never hard-coded); "Where it fits"

- Copy rules: first person, plain words, no em dashes, no brand or company names in UI copy.
